# Session and token storage inventory

## Key points

**Key points:** This inventory describes current `main` at `f1a9644f467da9a5e56162ff45a3450366827c8f`. It covers Manager sessions, API tokens, OIDC ID tokens, and Tachyon device session tokens. It does not claim that a normal log emits a token value.

**Detail:** Pending [#558](https://github.com/sixtyops/manager/pull/558) changes Tachyon request transport and diagnostics. Pending [#271](https://github.com/sixtyops/manager/pull/271) changes OIDC authentication and diagnostics. Neither is part of this current-main inventory. References below point to the inspected base commit.

## Manager sessions

**Key points:** Local login and the OIDC callback create the same 24-hour Manager session. Current `main` registers the generated ID and each successfully read stored ID with `register_secret`.

**Detail:** [`auth.create_session`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/auth.py#L263-L269) creates a UUID, registers it before persistence, and stores the ID, user name, IP address, and expiry in plaintext in SQLite through [`database.create_session`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L1857-L1863). Local login and OIDC callback call the same helper at [`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L973) and [`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3503). Both return an `HttpOnly`, `SameSite=Lax` cookie with a 24-hour max age. The `Secure` flag follows the request scheme or trusted proxy ([local login](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L980-L986), [OIDC callback](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3509-L3515), [proxy check](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/auth.py#L276-L289)). Requests do not extend expiry.

[`database.get_session`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L1866-L1877) returns only an unexpired row, then registers the stored ID. HTTP and WebSocket authentication use it ([HTTP](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/auth.py#L368-L372), [WebSocket](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/auth.py#L432-L438)). Logout deletes the session and its OIDC setting ([`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L1095-L1108)). Setup can delete all sessions ([`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L1082)). Startup and hourly cleanup remove expired sessions ([startup](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L532), [hourly cleanup](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L309-L314), [database cleanup](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L1892-L1904)). Login and logout audit calls do not include the session ID ([login](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L974), [logout](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L1098)).

[`logging_filter.register_secret`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/logging_filter.py#L105-L115) keeps registered values in the process registry, which sanitized output handlers apply ([handlers](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/logging_filter.py#L169-L178)). It does not encrypt the SQLite session table. The registration fix was tracked by [#518](https://github.com/sixtyops/manager/issues/518) and merged in [#519](https://github.com/sixtyops/manager/pull/519); it is already in this baseline.

## API tokens

**Key points:** Manager API tokens are stored as SHA-256 hashes. The full token is returned once at creation. Current `main` does not register the generated full value with `register_secret`.

**Detail:** [`auth.generate_api_token`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/auth.py#L304-L314) creates a `tach_` token from 32 URL-safe random bytes and returns the value, its hash, and a display prefix. [`app.create_token_api`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3659-L3705) stores the hash, prefix, owner, scopes, and optional expiry, then returns the full token in the response. The default expiry is none; callers may set 1 to 365 days. Authentication hashes the presented Bearer value, rejects expired tokens and missing or disabled owners, and updates `last_used_at` ([`auth._authenticate_bearer`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/auth.py#L317-L352)). There is no refresh flow. Listing omits the hash and full token ([`database.list_api_tokens`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L3580-L3592)); deletion revokes the row ([`database.delete_api_token`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L3604-L3614)); daily housekeeping deletes expired rows ([database cleanup](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L3616-L3622), [caller](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L270-L286)). Creation and deletion audit calls record the token ID and name, not its full value ([create](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3703-L3705), [delete](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3718-L3720)). The inspected authentication path does not log the presented Bearer value.

The uncovered path is registration of the generated full token. This is a source-coverage gap; this inventory did not reproduce a normal log leak. Track the source-registration work in [#578](https://github.com/sixtyops/manager/issues/578).

## OIDC ID tokens

**Key points:** The callback receives an ID token from the provider, validates it, registers it during encrypted storage, and retains it for provider logout. Manager has no ID-token refresh flow.

**Detail:** The token exchange returns the ID token at [`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3431-L3445). The callback decodes and validates its claims before accepting the session ([validation](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3450-L3483)). It stores the accepted token under a key containing the Manager session ID at [`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3503-L3506). The `oidc_id_token_` prefix marks the setting as secret ([`database.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L49-L57)). `database.set_setting` encrypts it before persistence ([setting write](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L1535-L1545), [encryption](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/crypto.py#L63-L66)); encryption registers the clear value. Reads register during decryption, or through the legacy plaintext hook ([decryption](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/crypto.py#L69-L74), [legacy read](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L1490-L1501)).

The callback logs provider error and exception text before storage registration at [`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3374), [`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3412), [`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3442), and [`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L3482). These are possible output paths, not proof that a log emits the ID token. Logout uses and deletes the value ([`app.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/app.py#L1103-L1127)). Removal follows Manager logout, expired-session cleanup, or per-user session deletion; there is no separate ID-token expiry cleanup ([session cleanup](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L1892-L1904), [user deletion](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/database.py#L3384-L3396)). Pending OIDC logging work stays separate in [#271](https://github.com/sixtyops/manager/pull/271).

## Tachyon device session tokens

**Key points:** Tachyon login tokens are kept in client memory and temporarily in a cookie file. They are not stored in the Manager database. Current `main` does not register them with `register_secret`.

**Detail:** [`TachyonClient.login`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L239-L315) creates a temporary cookie jar, reads the device `token` cookie into `self._token`, then attempts to remove the file. Cleanup failure logs a warning. Authenticated requests send the token as a cookie header ([shared curl](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L194-L196), [firmware upload](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L485-L493)). Poller clients are cached in memory. Ordinary clients expire ten minutes after last use or when disabled or removed ([cache](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/poller.py#L142-L158), [read refresh](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/poller.py#L198-L204)). At the inspected baseline commit, CPE clients expired ten minutes after cache insertion ([cache expiry](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/poller.py#L163-L187)); current code keeps them until the session check rejects the token or Manager credentials change. A session check uses the cached token; the poller logs in again after rejection ([check](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L316-L340), [poller](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/poller.py#L579-L603)). Manager does not enforce the cookie expiry or refresh the device token. A lab test confirmed a CPE session stayed valid after its password changed; see [#634](https://github.com/sixtyops/manager/issues/634).

Nearby output paths include login stderr and a response excerpt ([`client.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L273-L292)); upload stderr, response, and error data ([`client.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L503-L517)); and update-trigger error text or response data ([`client.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L545-L548)). Shared [`TachyonClient._curl`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L225) puts curl stderr in a raised exception. Config fetching propagates that text ([`fetch_config`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L1002-L1008)); `get_config` logs errors ([`client.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/vendors/tachyon/client.py#L1024-L1028)); and the config poller logs error details ([`poller.py`](https://github.com/sixtyops/manager/blob/f1a9644f467da9a5e56162ff45a3450366827c8f/updater/poller.py#L1067)). Login and authenticated curl subprocess arguments also include credentials or the session cookie. These are possible output paths, not proof that a log emits the token. Track device-token source registration in [#579](https://github.com/sixtyops/manager/issues/579). Pending transport diagnostics stay separate in [#558](https://github.com/sixtyops/manager/pull/558).
